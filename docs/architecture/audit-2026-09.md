# Maintainability audit — September 2026

This review examined application modules, cross-layer imports, duplicated rules,
Lambda persistence flows, infrastructure, build/deployment configuration, test
selection and project documentation. It is a source review with automated regression
checks, not a load test or proof that every production failure mode is covered.

## Baseline evidence

- 41,891 lines under frontend/backend/infrastructure source, including tests.
- 63 Jest suites / 1,005 tests passed initially; infrastructure reported no tests.
- 215 Playwright tests existed, but deployment selected only planner, shopping and
  language files. Lint and all Jest suites were absent from the deployment gate.
- `test:unit` selected property tests too. The pre-commit shell did not fail fast and
  bumped the app version before validation, without updating the lockfile version.
- Large production modules included InventoryList (1,357 lines), RecipeEditor
  (1,177), AddItemPage (1,073), inventory Lambda (927), shopping page (843), recipe
  Lambda (733), meal planner (710). The 2,652-line translation catalog is data,
  not equivalent to a 2,652-line controller.
- Three instruction/context sources repeated conventions. Maintained docs mixed
  deployed routes with planned receipt, shopping generation and sync endpoints.

## Remaining gaps and implementation order

These are outstanding work, not claims of fixes. Priorities reflect correctness and
change risk rather than file size alone. Each item has a completion criterion.

### Follow-through completed in this release

- Online npm audit found 24 advisories in the starting lockfile (one critical).
  Compatible dependency updates, Vite 6.4.3 and a documented Quagga 1.12.0 browser-bundle
  pin reduced the audited lockfile to zero known advisories. This is dependency advisory
  evidence, not a penetration test or proof of absence of vulnerabilities.

- All 215 browser journeys passed on a fresh dedicated server. The prior blank-page
  failure did not recur. Concurrent shared-package rebuilding remains an unconfirmed
  explanation, not an established root cause. Do not rebuild while browser tests run.
- Inventory and shopping now share complete pagination, cursor-loop detection and
  cancellation. Backend cursors reject malformed keys and foreign user partitions.
- Storage-location queries and recipe inventory/dependency queries follow every page.
  Location deletion uses a strongly consistent base-table query filtered by `location`,
  replacing the incompatible location GSI lookup. This fixes existing-reference checks;
  it does not eliminate races with simultaneous location/item mutations.
- Mutation envelopes reject JSON null, arrays and primitives. Location names and
  inventory text/quantity fields reject incorrect runtime types. Complete field schemas
  for every endpoint remain outstanding.
- Shopping loading has a feature hook with stale-response, cancellation, account-isolation,
  retry and reconnect tests. Other page-controller extractions remain incremental work.
- Service-worker cache matching recognizes Vite hashes and only deletes Pantry caches.
  Deployment preserves old assets for existing tabs. Assets are currently retained
  indefinitely; a reachability-aware cleanup policy is still needed.

### 1. Inventory consistency under concurrent writes — high

`backend/src/handlers/inventory/inventory.ts` reads a group's total, computes the
next total in JavaScript, then writes it. Lot and group writes occur separately.
Two concurrent purchases can lose an aggregate increment; partial failure can leave
a stock lot and its group inconsistent. `syncVersion` is incremented but does not
make these operations atomic by itself. Group creation also uses read-then-put.

Implement conditional/transactional lot + group writes, including reassignment,
deletion and threshold transitions. Define retry/idempotency semantics and reconcile
existing totals. Completion requires concurrent add/update/delete and injected partial
failure tests against DynamoDB semantics, plus a dry-run reconciliation report.
Do this before scaling to frequent writes from multiple devices.

### 2. Availability semantics disagree across features — high

Recipe `computeAvailability` and the frontend recipe availability index aggregate by
lowercased name and raw quantity. Shopping uses compatible units, explicit groups,
expiration and stock allocation. A recipe can therefore show sufficient stock even
when shopping correctly reports a shortage (for example grams versus kilograms or
expired lots). The rules were extracted unchanged to expose this mismatch safely.

Define one allocation contract with explicit legacy-unit and missing-link behavior;
use it for recipe detail, recipe filters and shopping. Completion requires cases for
mixed dimensions, conversions, repeated ingredients, linked groups, expired lots,
unknown handful quantities and non-mutation of input data. Preserve shopping's
existing ambiguity warnings instead of silently choosing a product.

### 3. Database pagination and uniqueness — high

Pagination and the incorrect location GSI lookup are fixed as described above.
Name uniqueness and last-location/reference guards still use read-then-write decisions,
which do not protect against simultaneous writes.

Introduce tested repository queries that follow every page and explicitly model
category/location access patterns. Make name uniqueness conditional, not read-then-write.
Completion requires >1 MB query simulations, locations referenced by lots, stale reads
and concurrent same-name creation tests. Shared client pagination is implemented for
both shopping and the main inventory.

### 4. Request contracts and error classification — medium/high

Several handlers cast `JSON.parse` results to records; JSON `null`, arrays, malformed
pagination tokens and incorrectly typed fields are not handled consistently.
Frontend request payloads still include `Record<string, unknown>` and backend records
often carry unvalidated optional fields. Shared compile-time types do not validate JSON.

Introduce explicit request schemas at HTTP boundaries with stable 400 responses.
Validate pagination tokens against the authenticated partition. Preserve supported
legacy values and distinguish malformed input from dependency failures. Completion
requires malicious/malformed payload tables and contract tests for each mutation.

### 5. Large page controllers and navigation state — medium

AddItemPage, RecipeEditor, ShoppingListPage and MealPlanPage still combine form state,
async data, navigation and rendering. App's state-based routing works, but independent
optional fields make invalid return contexts representable. Browser deep links and
history are limited. InventoryList still owns several independently testable controls.

Extract feature hooks and cohesive sections when editing each feature; use a
discriminated navigation state for mutually exclusive destinations. Start with the
shopping snapshot/loading lifecycle and inventory editor normalization. Keep current
full-page flows. Completion requires cancellation, stale-response, save/retry and
contextual-return regressions at desktop and mobile sizes. A blanket file move or
immediate router/state-library migration would not itself resolve these concerns.

### 6. Test organization and coverage quality — medium

Some property suites mix UI and domain behavior and load AWS mocks to test arithmetic.
Browser files repeat login/API fixtures, and old issue-number names obscure ownership.
Mocked browser and SDK suites cannot verify IAM, real database transactions, Cognito,
or installed service-worker behavior. Blanket browser coverage of every input
combination would increase runtime without addressing those gaps.

Move pure tests with extracted rules (recipe filter/availability suites are migrated),
introduce reusable stateful feature fixtures incrementally, and rename issue-specific
suites when consolidating overlapping journeys. Add an isolated AWS integration lane
for the high-risk contracts above. Measure coverage by missing behaviors and mutation
failures before imposing arbitrary global percentages. Keep property seeds/replay paths.

### 7. Offline behavior, asset rollout and recovery — medium

The app caches assets but does not implement offline entity storage or queued writes.
The service-worker hash matching, cache scope and deletion during asset rollout are
fixed. Local shopping state is not cloud-backed.

Add browser tests against the production build/service worker; match the actual build
manifest, scope cache deletion to app-owned caches, and keep prior release assets for
a defined grace period. Design offline write conflict/idempotency semantics before
advertising offline CRUD. Provide export/recovery for important device-local shopping
state and test a real database restore, not only backup configuration.

### 8. Operational architecture and dependencies — medium

The single stack uses fixed production names and lacks an isolated integration/staging
environment. Broad table read/write grants, permissive CORS, limited application
observability and no documented recovery drill remain review areas. No live security
audit was performed here. Dependency advisories were checked and remediated as recorded
above; an npm audit result does not assess live configuration or application logic.

Add structured request logging, failure/latency alarms, budgets and a restore runbook;
parameterize a separate development environment without renaming production resources.
Schedule dependency/lockfile maintenance with full checks and review SDK bundling
versus runtime-provided versions. Split constructs only when ownership becomes clearer;
preserve CloudFormation logical IDs and inspect replacement impact.

## Validation record

Baseline and implementation checks are recorded in the delivery report. Before release,
run the full gate, synthesize/diff the real CDK stack, and manually inspect the live app.
Infrastructure unit tests replace code bundling only; they do not replace that synth.
The earlier sandbox browser launch failure is environmental and is not a passing test.
